Build a Procurement Glossary Entry for a Unit That Changes Between Documents

Published by San Techno.

A practical guide for Singapore procurement teams on writing a glossary entry that keeps a changing unit traceable across quotes, receipts and internal files, with clear ownership for conversions and a place for unresolved questions.

Why a changing unit needs its own glossary entry

A unit that changes between documents is not a single problem to solve once. It is a recurring recordkeeping question. A quote may describe a quantity in one way, a delivery note in another, and an internal request form in a third. If the glossary simply picks a favourite wording, the file loses the ability to show what each document actually said.

The better approach is to treat the glossary entry as a small controlled record. It should hold the source wording exactly as written, note which document used it, and record who is allowed to confirm a conversion. That way a reader can follow the trail without guessing.

This matters in silicon and solar material files, where a purchasing team may handle semiconductor materials, solar grade silicon, wafer reclaim enquiries and power module documentation in the same folder structure. The glossary is not a technical specification. It is an administrative aid that keeps language consistent without overwriting the original.

A useful test: if a colleague opened the file a year later, could they see the original unit, the document it came from, and the person who confirmed any conversion? If not, the entry is incomplete.

Preserve the source words before you normalise anything

The first rule is preservation. Copy the unit exactly as it appears in the source document, including any abbreviation, spacing or capitalisation. Do not tidy it in the glossary. Put the tidy version in a separate field labelled as an internal preference.

A simple three-column layout works well. Column one is the source wording. Column two is the document reference, such as a quote number or a receiving note reference. Column three is the internal preferred wording, clearly marked as a preference rather than a correction.

For example, a fictional supplier quote might describe a quantity as a number of pieces, while the internal request form uses a different count. The glossary records both, with the quote reference beside the first and the request reference beside the second. Neither is deleted.

This habit also helps when a supplier changes its own wording between revisions. The old wording stays visible, and the new wording is added with its own reference. Readers can then see the change rather than discovering it by accident.

Keep the glossary free of engineering parameters. It is a language record, not a specification. If a document includes technical detail, the glossary should point to the document rather than reproduce it.

Decide who can confirm a conversion

A glossary entry should name a role, not a person, for conversion confirmation. Typical roles are the buyer who owns the file, the receiving team that records the arrival, and a technical contact who can confirm what a unit refers to in context. The glossary records which role confirmed what, and on what date.

This separation matters because a conversion is often not a purchasing decision. Purchasing can record that a document used one wording and another document used a different one. Confirming that the two refer to the same quantity may need the team that issued the original document.

A short confirmation line is enough: role, date, document reference, and the wording confirmed. Avoid copying personal contact details into the glossary. The role and the document reference are the useful parts.

Where a conversion cannot be confirmed, do not invent one. Leave the field open and add the question to the unresolved list described below. A glossary that shows an open question is more trustworthy than one that hides it behind a confident-looking number.

For context on how San Techno describes its own material work, the company notes that it helps recover non-usable silicon from integrated-circuit fabs, silicon wafer manufacturers, solar cell companies and chip packaging facilities. That is background for readers, not a conversion rule.

Where to place unresolved questions

Every glossary entry should have a companion list for questions that procurement cannot answer. Keep it short and specific. Each item should name the document, the wording in question, the role that might answer it, and the date the question was raised.

A fictional example: a receiving note uses a count that does not match the quote reference. The glossary records both wordings. The unresolved list records the question, assigns it to the receiving team lead, and notes that no conversion has been confirmed. Nothing is assumed.

This list is also useful during handovers. When a file moves between teams, the open questions travel with it. A new owner can see what is still outstanding without reading every document.

Keep the list separate from the glossary table itself. Mixing confirmed and unconfirmed entries in one column invites readers to treat an open question as settled. A clear visual or structural separation is enough.

Review the list at a set interval, such as before a file is closed or when a document set is revised. The interval is a working habit, not a rule. The point is that open questions get a second look rather than quietly ageing in a folder.

Keep the glossary consistent with the rest of the file

A glossary entry is only useful if the surrounding file agrees with it. That means the same wording should appear in the request form, the receiving record and any internal summary. Where it does not, the glossary should note the difference rather than silently harmonise it.

A practical worksheet helps here. List each document in the file, the unit wording it uses, and whether the glossary entry matches. Mark each row as matching, different, or not yet checked. This gives a quick view of where the file is consistent and where it is not.

This is also where related reference material earns its place. A team that keeps a small set of public reference notes can point readers to the right place without copying content into the glossary. San Techno's public resources area is one example of where a reader might look for general company information, while the products area describes the company's material and design work. Neither replaces the glossary, but both help a reader understand the context of a file.

Keep the worksheet administrative. It records wording and references, not technical judgements about the material itself.

A short worked example with fictional counts

Suppose a fictional file contains three documents. A quote describes a quantity as 40 units. A receiving note describes the same delivery as 4 boxes. An internal request form describes it as 40 pieces.

The glossary entry records all three wordings with their document references. The internal preference field notes that the team uses pieces in its own forms. The conversion field is left open, with a question assigned to the receiving team lead asking whether the box count and the piece count refer to the same delivery.

No one writes that 4 boxes equals 40 pieces until the receiving team confirms it. If they do confirm, the glossary records the role, the date and the document reference. If they do not, the question stays open and the file shows that clearly.

This example is deliberately simple. Real files may have more documents and more wordings. The principle is the same: preserve, separate, confirm, and leave open questions visible.

The example also shows why the glossary should not be merged with a technical specification. The glossary is about language and traceability. Technical questions belong with the team that can answer them.

Review the entry when documents change

A glossary entry is a living record. When a supplier issues a revised quote, a new receiving note arrives, or an internal form is updated, the entry should be checked against the new document. Add the new wording with its reference rather than replacing the old one.

A short review note is enough: what changed, which document introduced the change, and whether any earlier conversion is affected. This keeps the history readable without turning the glossary into a long narrative.

Where a document set is large, a simple index of glossary entries by document reference helps readers find the right entry quickly. The index is administrative and should not include confidential material.

Finally, keep the glossary within the scope it was designed for. It records wording, references and confirmations. It does not decide what a material is, whether a delivery is acceptable, or how a unit should be interpreted technically. Those questions belong with the teams that own them, and the glossary should point to them rather than answer them.
