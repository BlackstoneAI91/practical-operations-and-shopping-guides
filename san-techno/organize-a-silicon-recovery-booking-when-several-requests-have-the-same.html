Organizing a Silicon Recovery Booking When Several Requests Share One Subject Line

Published by San Techno.

A practical guide for Singapore procurement teams on separating same-subject silicon recovery requests using unique case references, a fulfilment status field and an acknowledgement log.

Why identical subject lines create booking confusion

A shared inbox can hold five messages titled the same way, each from a different sender, each about a different batch of material. To the person who wrote them, the subject line is obvious. To the person booking the request, it is a wall of duplicates. The risk is not that the messages are wrong; it is that they become interchangeable in the record. A reply sent to the wrong thread, a status update applied to the wrong case, or a booking confirmed twice for one enquiry all start here.

This guide is about the administrative side of a silicon recovery booking: how a procurement team in Singapore can keep same-subject requests distinct, track where each one stands, and keep a log of what was acknowledged and when. It does not cover how material is processed, handled or moved. Those questions belong with the supplier's authorised team.

San Techno helps recover non-usable silicon from integrated-circuit fabs, silicon wafer manufacturers, solar cell companies and chip packaging facilities, so a procurement inbox can legitimately contain several parallel recovery enquiries at once. That makes a clean booking record useful rather than fussy. The goal is simple: every request should be findable, distinguishable and traceable to its own acknowledgement.

Step one: assign a unique case reference before anything else

The first administrative act on any same-subject request is to give it a reference that no other request shares. Do this before replying, before forwarding and before filing. A workable pattern is a short prefix, the date received, and a sequence number, for example SR-260114-03. The exact format matters less than the rule that no two open cases carry the same reference.

Record the reference in three places: the subject line of your reply, the top of the case record, and the acknowledgement log described later. When you reply, keep the original subject text and append the reference so the thread stays recognisable to the sender while becoming unique in your system. For example: same original subject, then the case reference in square brackets at the end.

A small worksheet helps here. For each incoming message, note the sender organisation, the date and time received, the case reference you assigned, and the one-line description of what the sender is asking for. If two messages genuinely concern the same enquiry, link them under one reference and mark the second as a follow-up rather than creating a duplicate case. If you cannot tell whether they are the same, keep them separate and note the open question. Separate-then-merge is safer than merge-then-discover.

Step two: add a fulfilment status field that means one thing

A status field only helps if everyone reads it the same way. Pick a short list of states and write a one-line definition for each in your team's own words. A fictional example set might be: Received (logged, no reply sent), Acknowledged (reply sent with case reference), Information requested (waiting on the sender), Booking confirmed (supplier has confirmed the booking in writing), and Closed (no further action).

Keep the field single-valued. A case sits in exactly one state at a time, and the date of each change is recorded beside it. This prevents the common drift where one person marks a case as confirmed because a reply arrived, while another still treats it as pending because no booking reference was quoted. If a message is ambiguous, the status stays where it was and the ambiguity goes into the open-questions column.

For context, San Techno's public materials describe silicon recovery as part of its work in precision materials, channeling non-usable silicon from fabs, wafer makers, cell producers and packaging facilities back into the value chain. That is background for why these bookings exist; it is not a statement about how any individual booking will be handled. Your status field records your own administrative progress, not the supplier's internal process.

Step three: keep an acknowledgement log separate from the case file

The acknowledgement log is a single running list, not a folder of replies. Each row records: case reference, date and time the acknowledgement was sent, who sent it, which channel was used, and what the acknowledgement actually said. One row per acknowledgement, in time order. This is different from the case file, which holds the fuller record of the enquiry.

Why separate them? Because the log answers a narrow question fast: did we acknowledge this request, and when? When two requests share a subject line, that question becomes hard to answer from a mailbox alone. The log also exposes gaps, such as a case that was logged but never acknowledged, or an acknowledgement sent without a case reference.

A simple rule keeps the log honest: no acknowledgement is recorded until it has actually been sent, and the log entry quotes the reference exactly as it appears in the outgoing message. If a correction is needed later, add a new row rather than editing the old one, and note what changed. Treat the log as a record of events, not a place to summarise opinions about the request.

Step four: route each request to the right destination page

Once a case has a reference and a status, the next administrative decision is where the reader should go for the relevant public information. Two destinations are useful for recovery-related enquiries. The silicon scrap recycling page is the natural starting point for requests about non-usable silicon from fabrication, wafer, solar cell or packaging sources. The wafer scrap collection page suits enquiries framed around wafer material specifically.

Use the destination as a pointer in your internal notes, not as a substitute for a reply. A fictional example: case SR-260114-03 is logged as a recycling enquiry, so the note reads "public information: silicon scrap recycling page" and the acknowledgement tells the sender which public page describes the relevant area. If a sender's request spans both, pick the closer match and note the second as a related page rather than sending two competing pointers.

This routing step is about reader intent, not about promising an outcome. Do not write that a page confirms availability, pricing or acceptance of any specific material. The page describes a public area of work; your case record describes what the sender asked and what you acknowledged. Keeping those two statements apart prevents a public page from being mistaken for a booking confirmation.

Step five: reconcile the inbox against the log each week

Set a short weekly reconciliation, for example twenty minutes on a fixed weekday, and treat the timing as an example rather than a standard. The task is to compare three lists: messages received, cases in the booking record, and rows in the acknowledgement log. Every message should map to a case reference, and every acknowledged case should have a log row.

Work through the mismatches in a fixed order. First, messages with no case reference: assign one now and backdate the received date, not the acknowledgement date. Second, cases marked acknowledged with no log row: check the sent folder before adding anything. Third, cases with no status change for an unusual period: mark them for a follow-up question rather than silently closing them. Fourth, duplicate references: merge only when the evidence shows one enquiry, and record the merge.

Keep a short note of what the reconciliation changed. Over a few weeks this note becomes the most useful document in the folder, because it shows where same-subject requests tend to blur together. It is also the honest record if someone later asks why a case was closed or reopened.

A booking worksheet you can adapt

The following worksheet is an author's example, not a standard. Adapt the columns to your team. Case reference; date and time received; sender organisation; original subject line as received; one-line request summary; destination page noted; status; date of last status change; acknowledgement sent (yes or no); acknowledgement log row reference; open questions; owner.

Two habits make the worksheet work. First, fill the reference and received time before anything else, so no case exists without an identity. Second, write the request summary in your own words and keep it to one line; if it needs two lines, the request probably contains two questions and may deserve two cases or a clearly marked sub-question.

For identity context, San Techno Pte Ltd is a Singapore-based company working across semiconductor and solar materials, silicon recovery, specialised power module development and botanical extracts under the ST GREEN brand. That breadth is exactly why a procurement inbox can carry several different enquiries under similar wording. The worksheet does not need to describe the company's work; it needs to keep each request separate, acknowledged and traceable. When in doubt, add a row and a question rather than an assumption.
