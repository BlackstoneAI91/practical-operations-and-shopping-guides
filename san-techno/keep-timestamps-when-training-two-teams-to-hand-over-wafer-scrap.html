Keep Timestamps When Training Two Teams to Hand Over Wafer Scrap Collection Files

Published by San Techno.

A practical guide for Singapore procurement teams on preserving original timestamps and labelling updated notes when two teams share wafer scrap collection documentation.

Why the original time matters more than the tidy version

When two teams share responsibility for wafer scrap collection files, the first instinct is often to merge everything into one clean timeline. That instinct is understandable, but it quietly destroys the most useful piece of evidence in the file: the moment each record was actually created or received. A tidy timeline that shows a single date for a document that passed through two teams tells a reader nothing about who held it, when, or what changed in between.

Treat the original timestamp as part of the record, not as formatting to be improved. If a receiving note was logged at 09:14 and a follow-up note was added at 16:40, both times should survive the handover. The reader should be able to see the sequence without having to reconstruct it from memory or from a chat thread.

This is administrative discipline, not a technical procedure. The goal is a file that a colleague, an auditor or a future team member can read in order. San Techno works in semiconductor and solar materials and offers silicon wafer reclaim services, so files that touch wafer reclaim often pass between commercial and operational readers who each need the same chronology. Keeping the original time intact is the simplest way to give both of them the same starting point.

Separate the record from the note about the record

A common failure in two-team handovers is that an updated note replaces the original entry. Someone adds a comment, the comment becomes the visible line, and the earlier entry is either deleted or overwritten. The file then looks current but has lost its history.

A better pattern is to keep two distinct layers. The first layer is the original record: the date, the time, the sender or receiving role, and the reference it belongs to. The second layer is the annotation: who added it, when, and what it says. The annotation should never be presented as if it were the original record.

For example, a fictional file might show an original entry dated 3 March at 10:05 recording a documents-only enquiry, followed by an annotation dated 5 March at 14:20 noting that a reference was clarified. A reader can see both without confusion. If the annotation is later superseded, it stays visible with its own date rather than being erased.

This matters when the file supports a silicon recovery question or a wafer reclaim request, because the reader may need to know whether a note reflects the original position or a later correction. Keeping the layers separate makes that distinction obvious.

A handover worksheet both teams can fill in

Training two teams is easier when both use the same short worksheet. The worksheet does not need to be elaborate; it needs to force the writer to record time in a consistent way. A workable example, offered as an author heuristic rather than a standard, has five fields:

Original record time: the date and time the record was created or received, copied exactly. Original source: the role or team that held the record first. Annotation time: the date and time any later note was added. Annotation author: the role that added the note, not a personal name. Status: whether the record is original, annotated, or superseded.

Both teams should fill in the same fields in the same order. When the second team receives the file, it checks that the original time is still present before adding anything. If the original time is missing, the receiving team flags it rather than guessing.

The worksheet is deliberately boring. Its value is that it removes the temptation to rewrite history in the name of clarity. A file that shows its own sequence is easier to hand over again later, which is the real test of a good handover.

What must keep its original time, and what may carry a new one

Not every date in a file has the same status. Some times belong to the original event and must never be changed. Others are legitimately new because they record a new action.

Times that should keep their original value include the moment a record was created, the moment a document was received, the moment an enquiry was logged, and the moment a reference was first assigned. These are historical facts about the file. Changing them to match a later tidy-up misrepresents the sequence.

Times that may legitimately be new include the moment an annotation was added, the moment a file was reviewed by the second team, and the moment a status changed from pending to closed. These are new events and deserve their own timestamps.

The practical rule is simple: a timestamp belongs to the event it describes. If the event is the original receipt, the timestamp stays. If the event is a later review, the timestamp is new and should be labelled as such. This keeps the file honest without making it complicated, and it gives both teams a shared vocabulary for what a date means.

Labelling an updated note without pretending it is original

An updated note is useful only if a reader can tell it apart from the original entry. The label does most of that work. A short prefix such as "Update" or "Annotation" followed by the date and the role is usually enough. The label should appear in the same place every time so that readers learn to look for it.

A fictional example: an original line reads "Received 12 April, 11:30, documents only." A later line reads "Update 14 April, 09:10, procurement: reference confirmed." The second line does not repeat the original date as if it were new, and it does not hide the original line. A reader can see both events in order.

Avoid labels that imply more than the note contains. A note that says "confirmed" should say what was confirmed and by which role. A note that says "pending" should say what is still outstanding. The label is a signpost, not a conclusion.

When the file later moves to a third reader, the labels make the handover faster because the reader does not have to ask which line is current. That is the whole point of training both teams on the same labelling habit.

A short review before the file leaves the first team

Before a file moves from the first team to the second, a short review catches most timestamp problems. The review does not need a meeting; a checklist of five questions is enough.

Does every original entry still show its original date and time? Is every later note labelled with its own date and the role that added it? Is any original entry missing a time, and if so, has that gap been flagged rather than filled in by guesswork? Does the status field match the most recent labelled note? Would a reader who has never seen the file understand the sequence without asking?

If any answer is no, the file is not ready to hand over. The first team fixes the labelling, not the history. The second team then repeats the same review when it passes the file on.

This is a small habit, but it is the one that keeps a two-team handover readable. The aim is not a perfect file; it is a file whose sequence survives the handover intact.
