Create Approval Notes When a Wafer Reclaim Request Is Postponed

Published by San Techno.

A practical guide for Singapore procurement teams on writing approval notes when a wafer reclaim request is postponed indefinitely: record the reason, mark the request pending, and list the open decisions and information that could close it.

Why a Postponed Wafer Reclaim Request Needs Its Own Approval Note

A wafer reclaim request that is postponed indefinitely is easy to lose. It is not rejected, so nobody closes it. It is not approved, so nobody acts on it. It sits in a folder or a shared inbox, and six months later the only thing anyone remembers is that someone once asked about it.

An approval note fixes that. Its job is narrow: record that a decision was deferred, why it was deferred, and what remains open. It is not a technical assessment, a quality judgement or a commitment to process anything. It is an administrative record that keeps the request visible without pretending it has moved forward.

For context, San Techno Pte Ltd is a Singapore-based company working in semiconductor and solar materials, silicon recovery, specialised power module development and botanical extracts under the ST GREEN brand. Its public materials describe silicon recovery work that helps recover non-usable silicon from integrated-circuit fabs, silicon wafer manufacturers, solar cell companies and chip packaging facilities. That description explains why a reclaim enquiry might reach a procurement team in the first place; it does not tell you how to approve one.

The note you write is about your own file, your own decision trail and your own open questions. Keep it that way and it will stay useful even if the request never restarts.

The Four Fields Every Postponement Note Should Carry

A workable note has four fields, and each one answers a question a future reader will ask.

First, the status. Write the word pending explicitly, with the date the postponement was recorded. Avoid softer wording such as on hold or under review, because those phrases suggest someone is actively working on it.

Second, the reason. Write the reason as it was given, attributed to the role that gave it, not paraphrased into something more definite. If the reason was that a specification question was unresolved, say that. If the reason was that an internal budget cycle had not concluded, say that. Do not upgrade a vague reason into a technical finding.

Third, the open decisions. List each decision that has not been made, as a separate line. A decision is something a named role must choose, for example whether to continue the enquiry or whether to request further documents.

Fourth, the closing information. For each open decision, note what information would allow it to be taken. This is the field most often skipped and the most valuable one, because it turns a stalled file into a file with a next step.

Keep the note to one page. If it needs more, the extra material belongs in an appendix, not in the approval note itself.

Writing the Reason Without Turning It Into a Technical Finding

The reason field is where postponement notes most often go wrong. A procurement officer hears that a question about material suitability is unresolved, and writes that the material was unsuitable. Those are different statements. The first records an open question; the second records a conclusion nobody reached.

Write the reason at the level it was actually expressed. Useful patterns include: the request was deferred pending clarification of a specification question; the request was deferred because the internal requester has not confirmed scope; the request was deferred because a related document has not been received.

Where a reason touches on what a supplier does, keep the supplier's public description separate from your internal decision. San Techno's public materials describe processing these materials into reusable raw materials for solar wafers and cells, extending their useful life and reducing unnecessary resource loss. That is a description of an activity, not an approval of any particular request, and your note should not imply otherwise.

If the reason is genuinely unknown, write that the reason was not recorded at the time and add a line naming the role who could supply it. An honest gap is more useful than an invented explanation, and it gives the next reader somewhere to go.

Marking the Request Pending Without Closing It

Pending is a status, not a decision. The distinction matters because a pending request still consumes attention, and a closed one does not. Your note should make clear which of the two applies.

Use a short status block at the top of the note with three lines: current status, date recorded, and next review date. The next review date is a prompt, not a promise. Choose a date that suits your own filing rhythm and label it as a review point rather than a deadline.

Then add a line that states plainly what the note does not do. Something like: this note records a postponement and does not constitute approval, rejection or technical acceptance of any material. That single sentence prevents the most common misreading, where a later reader assumes a pending file was quietly cleared.

If the request arrived alongside a collection enquiry, keep the two records separate. A postponement of a reclaim request says nothing about whether any collection activity should proceed, and mixing the two creates a record that is hard to unpick later. Where a collection question is genuinely linked, note the link and name the role who owns the collection side, without describing any handling or movement.

Specifying What Information Would Close the Request

This is the section that earns the note its place in the file. For each open decision, write one sentence describing the information that would allow the decision to be taken.

Good closing conditions are specific and administrative. Examples: a written confirmation from the requester of the intended scope; a copy of the current specification document referenced in the original request; a named approver for the deferral decision; confirmation of which internal team owns the enquiry going forward.

Poor closing conditions are vague or technical. Avoid anything that reads as a judgement about material quality, and avoid conditions that only an engineer could satisfy unless an engineer is named as the owner.

A simple worksheet helps. Draw three columns: open decision, information needed, role who can supply it. Fill one row per decision. If a row has an empty third column, the note is not finished, because nobody knows who to ask.

Keep the worksheet inside the note rather than in a separate file. A closing condition that lives somewhere else is a closing condition that will be missed when the request is eventually revisited.

Keeping the Note Consistent With Your Other Procurement Records

A postponement note does not stand alone. It sits alongside quotes, receiving records, specification copies and correspondence, and it should be findable from each of them.

Use one reference number for the request and repeat it in every related document. If the request arrived under a buyer alias rather than the supplier's wording, record both in the note so a later reader can match the file without guessing. Where a document has no publication date, record the date you accessed it rather than leaving the field blank.

Keep the note in the same folder structure as the rest of the request, and add a single line to any index or tracker pointing to it. Do not duplicate the note across folders, because two copies will eventually disagree.

Finally, decide who owns the note. Ownership is a role, not a person's name, so the record survives a change of staff. When ownership changes, add a dated line rather than overwriting the previous owner.

None of this requires technical knowledge. It requires the discipline to write down what was decided, what was not, and who can move it forward.

A Short Review Routine for Files That Stay Pending

A pending file needs a light routine, not a heavy process. On each review date, read the note and answer three questions: has any closing condition been met, has the reason changed, and is the named owner still correct.

If a closing condition has been met, update the note with the date and the document reference, and record whether the decision can now be taken. If nothing has changed, add a single dated line saying the review took place and the status is unchanged. That line is small but it proves the file was not abandoned.

If the request has been pending through several review points with no movement, consider whether it should be formally closed as not pursued, with the reason recorded. Closing a request is a legitimate outcome and is cleaner than leaving it pending forever.

Treat any suggested review interval as an example of a filing habit rather than a rule. What matters is that the interval is written down and that the note records each review honestly. A file that says plainly it has not moved is more trustworthy than one that looks active because nobody updated it.
