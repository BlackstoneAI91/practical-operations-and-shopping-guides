Fixed Pickup Window vs Confirmed Collection Slot: A Procurement Guide

Published by San Techno.

A practical guide for Singapore procurement teams on recording default pickup availability separately from a confirmed collection slot, keeping provisional and confirmed fields distinct, and retaining the latest acknowledgement for wafer scrap and silicon recovery collections.

Why the two records must stay separate

A fixed pickup window and a confirmed collection slot answer different questions, and mixing them in one field is where most receiving-desk confusion begins. A fixed pickup window describes default availability: the days or hours a site normally presents material for collection, stated in advance and not tied to any particular lot. A confirmed collection slot is a specific booking: a date, a time band and a reference that someone has acknowledged for one identified consignment.

The practical risk is that a default window gets copied into a booking field, or a provisional request gets treated as confirmed because it sits in the same spreadsheet column. When that happens, the receiving desk prepares for a collection that was never actually agreed, or holds material back because a default window was read as a firm appointment.

For teams handling semiconductor materials and solar grade silicon, the distinction matters because the material itself is often staged, counted and labelled before the collection. A wrong assumption about the slot can leave staged inventory exposed or block a dock position that another consignment needed.

San Techno Pte Ltd works in semiconductor and solar materials, including silicon recovery, and its public materials describe recovering non-usable silicon from integrated-circuit fabs, silicon wafer manufacturers, solar cell companies and chip packaging facilities. That context is useful because it tells you the collection conversation usually involves a vendor who handles the material onward, not a general courier. Keep the record administrative: what was agreed, for which lot, and on what evidence.

Define the fields before the first booking

The cleanest way to avoid the fixed-versus-confirmed muddle is to decide, in advance, which fields belong to which record. A short field dictionary agreed by purchasing and the receiving desk is enough; it does not need to be elaborate.

Suggested field set, offered as an author heuristic rather than a standard:

Default availability record: site or dock identifier, normal collection days, normal time band, blackout periods, access notes that are safe to share, and the date the default was last reviewed.

Specific booking record: booking reference, material description, lot or package count, requested date and time band, status (requested, provisional, confirmed, cancelled), the acknowledgement that supports the status, and the date the status last changed.

Two rules keep these apart. First, a default window may be copied into a booking request as a starting suggestion, but it must never set the status to confirmed. Second, only an acknowledgement that names the specific booking can move a record from provisional to confirmed.

Label the status field explicitly rather than relying on colour or position in a sheet. A reader who opens the file six weeks later should be able to tell, from the words alone, whether the slot was agreed or merely hoped for.

Recording default availability without implying a booking

Default availability is genuinely useful. It tells a buyer when a site can normally present material, and it shortens the conversation about which days are realistic. The problem is only when a default is mistaken for a commitment.

Write the default in its own section of the record, headed clearly as availability rather than appointment. Add a line stating that the default does not constitute a booking and that each collection requires a separate confirmed slot. That single sentence prevents most of the misreading.

Review defaults on a schedule you choose, for example each quarter, and record the review date. Sites change dock arrangements, staffing and access rules, and an unreviewed default quietly becomes wrong. When a default changes, note what changed and when, so a booking made under the old default can be rechecked.

For material that will move into wafer reclaim or silicon recovery, the default window is only the outer frame. The specific booking still has to identify the lot, the package count and the documentation that will travel with it. Treat the default as background information and the booking as the operative record.

What a confirmed collection slot should contain

A confirmed slot is a small, self-contained record. If someone unfamiliar with the file picked it up, they should be able to answer four questions: what is being collected, from where, when, and who acknowledged it.

Include the booking reference and the material description in plain words. Include the lot identifier or package count as agreed, not as estimated. Include the date and time band exactly as acknowledged, without rounding or tidying. Include the acknowledgement itself, or a pointer to where the latest version is stored.

Keep provisional and confirmed values in separate fields rather than overwriting one with the other. If a requested date of the twelfth becomes a confirmed date of the fourteenth, both should remain visible with their statuses, so the change is auditable. Overwriting destroys the trail and makes later questions about what was agreed impossible to answer.

Avoid writing carrier promises into the record. A confirmed slot is an agreement about a collection window; it is not a guarantee about transit, arrival at a downstream site, or processing outcomes. State only what was acknowledged, and route any question about onward handling to the party that owns it.

Retaining the latest acknowledgement

The acknowledgement is the evidence that turns a request into a confirmed slot, so its retention deserves a rule rather than good intentions. Keep the latest acknowledgement in a fixed location named in the booking record, and keep superseded versions rather than deleting them.

A simple version convention works: each acknowledgement gets a sequence number and a received date, and the booking record points to the current one. When a new acknowledgement arrives, update the pointer and leave the earlier file in place. The record then shows both the current position and how it was reached.

Name files so they can be matched without opening them, using the booking reference and sequence number. Store them where the receiving desk and purchasing can both reach them, and note who is responsible for filing each new acknowledgement.

When a collection is complete, close the record by marking the final acknowledgement as the closing evidence and noting the date. A closed record with a clear final acknowledgement is far easier to review later than a folder of loosely named files.

A short decision worksheet for the receiving desk

Use this worksheet when a collection record is opened or challenged. It is a set of prompts, not a scoring system.

Question one: is the date in the record a default window or a specific booking? If the field is headed availability, it is a default and cannot authorise preparation on its own.

Question two: what is the status word, and which acknowledgement supports it? If no acknowledgement names this booking, the status is at most provisional.

Question three: are provisional and confirmed values both visible? If one has overwritten the other, reconstruct the history before proceeding.

Question four: does the booking identify the lot and package count as agreed? If the count is an estimate, mark it as such rather than presenting it as confirmed.

Question five: is the latest acknowledgement filed and pointed to from the record? If not, file it before the collection date.

Question six: has anything changed since the acknowledgement, such as a revised default window or a new access note? If so, recheck the booking against the change.

A worked fictional example: a site records a default window of Tuesday and Thursday mornings. A buyer requests a Thursday slot for a staged lot and marks it requested. An acknowledgement naming the lot and the Thursday time band arrives and the status moves to confirmed, with the acknowledgement filed as sequence one. A later message moves the slot to the following Tuesday; sequence two is filed, the confirmed date is updated, and the original Thursday value remains visible as superseded. The receiving desk reads the record and prepares for Tuesday only.

Where this fits alongside your other collection records

This guide covers one decision: keeping default availability and a confirmed slot distinct. It sits alongside the other records a procurement team keeps for collections, and the same discipline of separate fields, explicit statuses and retained evidence carries across them.

When a collection is tied to material that will be processed onward, the booking record should also point to the manifest and any intake notes, so the receiving desk is not hunting across systems on the day. San Techno's public materials describe processing recovered silicon into reusable raw materials for solar wafers and cells, which is a reminder that the collection record is the front end of a longer chain and should hand over cleanly.

Keep the scope tight. This page does not cover carrier performance, transit timing or processing outcomes, and it should not be read as advice on those. It covers how to write down what was agreed, distinguish it from what is merely normal, and keep the acknowledgement that proves the difference.
