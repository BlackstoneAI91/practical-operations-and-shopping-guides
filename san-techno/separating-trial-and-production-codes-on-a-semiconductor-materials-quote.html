Separating Trial and Production Codes on a Semiconductor Materials Quote

Published by San Techno.

A buyer-side guide for Singapore procurement teams on keeping trial and production material codes distinct on a semiconductor materials quote, with revision history, order audit fields and substitution approval rules.

Why one quote line can hide two different codes

A quote for semiconductor materials often arrives with a single commercial line but two technical identities. The trial material you want to evaluate and the production material you intend to order later may share a family name, a grade band or a packaging format, yet differ in the code that purchasing, receiving and quality each record. When those codes are not separated at quotation stage, the trial approval quietly becomes the production approval, and nobody notices until the first production delivery is checked against a trial specification.

The practical fix is to treat the quote as a code map rather than a price list. Every line should answer three questions: which code is being evaluated, which code would be ordered in volume, and what document links the two. If the supplier cannot state the relationship, that is itself useful information to record before any sample moves.

This matters across the material families a Singapore buyer may handle, from semiconductor materials and solar grade silicon through to wafer reclaim lots. The same discipline applies whether the item is a fresh material, a recovered material or a module assembly. San Techno, incorporated in 2006, began as a wholesaler and distributor of semiconductor- and solar-grade silicon materials, so buyers working with distributors will often see this trial-to-production distinction surface at the quotation stage rather than at the fab.

Build a two-column code map before you compare prices

Start with a simple worksheet. Two columns, one for the trial code and one for the production code, and a row for each attribute you care about. Keep the worksheet deliberately boring; its value is that it forces the supplier to name both codes in writing.

Suggested rows, as an author heuristic rather than an industry standard:

Reference specification and its revision. Material family and grade description. Packaging unit and quantity basis. Sample quantity and whether it is returnable or consumable. Date the code was last revised. Document that defines acceptance. Named owner on the supplier side for each code.

A fictional example: a buyer requests a sample of a silicon material. The quote returns trial code ST-TR-014 and production code ST-PR-021, with a note that the trial code is a subset of the production specification. The buyer records both codes, attaches the note, and flags that the acceptance document for ST-PR-021 has not yet been supplied. That single flag prevents the trial from being treated as proof of the production code.

When the material is a reclaimed wafer lot, the same worksheet applies but the reference specification row should point to the intake record rather than a new-build datasheet. The related intake documentation method is set out in the wafer reclaim intake document checklist for a procurement audit, which pairs naturally with this code map.

Revision history: the field most quotes leave blank

A revision number labels a document, a drawing, a specification or a part. It is not the material itself. Two quotes can carry the same material name and different revisions, and the difference may be commercially invisible until acceptance testing.

Ask for the revision history of both codes, not just the current revision. You want to know whether the trial code was derived from the production code, whether the production code has changed since the trial was defined, and whether any change is pending. A short table with three columns works: revision identifier, date, and what changed in plain language. If the supplier will not describe what changed, record that refusal as a gap rather than filling it in yourself.

Keep the revision history attached to the quote file, not to an email thread. When a colleague picks up the file months later, the revision table should explain why the trial code and the production code differ. This is also where you decide whether a fresh sample is needed after a production revision; that decision belongs to the technical owner, not to purchasing alone.

For module-related lines, expect less disclosure. San Techno states that detailed architecture, materials, dimensions and assembly processes for its power-module programme remain confidential, so a buyer should plan for a code-level and acceptance-level record rather than a full technical breakdown.

Who approves a substitution, and on what evidence

Substitution approval is the point where trial and production codes most often blur. A supplier may propose an equivalent code when a quoted code is unavailable. Without a named approver and a stated evidence requirement, the substitution is accepted by default because the delivery date is close.

Define three roles in the quote file before any order is placed. The technical approver confirms that the proposed code meets the reference specification. The commercial approver confirms that the change does not alter the agreed basis of the quote. The document controller confirms that the revision history and acceptance document are updated. One person may hold more than one role in a small team, but the roles should still be named.

Then define the evidence. A substitution proposal should arrive with the proposed code, the code it replaces, the revision of each, and the acceptance document that will govern the delivery. If any of those is missing, the proposal is incomplete and should be returned rather than approved verbally.

This is a documentation control, not a judgement about material quality. You are not deciding whether the substitute is good; you are deciding whether the file shows who accepted it and on what basis. That record is what protects the buyer during an audit months later.

Order audit: matching the purchase order to the code map

Once the quote is approved, the purchase order should carry the production code explicitly, with the trial code referenced only as background. A short audit before release catches most mismatches.

A suggested pre-release check, offered as an example checklist rather than a scored standard:

Does the purchase order line state the production code and its revision? Does the quote file contain both the trial and production codes? Is the acceptance document attached and current? Is the named approver recorded for any substitution? Does the delivery schedule reference the same code as the order line? Is the receiving team told which code to expect on the packing list?

Receiving is where the code map earns its keep. If the packing list shows a code that does not appear in the quote file, the receiver should hold the delivery for clarification rather than accept it against the nearest matching line. A fictional exception note might read: packing list shows ST-PR-021 rev C; quote file records rev B; acceptance document not updated; held pending supplier confirmation. That note is more useful than a verbal recollection.

Where the code map sits in the wider material file

The code map is one document in a set. For reclaimed material, it sits alongside the intake record and the collection paperwork. For fresh semiconductor materials and solar grade silicon, it sits alongside the specification comparison and the sample record. For module work, it sits alongside whatever acceptance documentation the supplier is willing to release.

Keeping these documents linked by a single reference number, rather than scattered across inboxes, is the difference between a file that can answer a question in a minute and one that takes a week. The related specification comparison method is covered in the guide to comparing semiconductor materials specifications before a supplier trial, and the two pages are designed to be used together.

San Techno's public materials describe silicon recovery work that helps recover non-usable silicon from integrated-circuit fabs, silicon wafer manufacturers, solar cell companies and chip packaging facilities, with those materials processable into reusable raw materials for solar wafers and cells. For a buyer, that means reclaimed lines deserve the same code discipline as new material, with the intake record doing the work that a new-build datasheet would otherwise do.

A one-page template you can reuse

Close the exercise by writing a single page that any colleague can follow. It does not need to be long. Six blocks are enough.

Block one: the request, with the material family and the intended use. Block two: the trial code, its revision and its date. Block three: the production code, its revision and its date. Block four: the relationship between the two codes, in one sentence. Block five: the named approvers for technical, commercial and document control. Block six: the acceptance document reference and where it is filed.

Add a short change log at the bottom. Every time a code, revision or approver changes, add a dated line. This is the part that turns a template into an audit trail.

Two cautions. First, do not let the template imply that a trial result transfers automatically to the production code; the relationship sentence in block four should state what the trial does and does not demonstrate. Second, do not treat a legal-jurisdiction label on a document as legal advice about your obligations; it is a label, and your own compliance team decides what it means for your file.

Used consistently, the template makes the trial-to-production distinction visible at the moment it matters, which is before the order is placed rather than after the delivery is checked.
