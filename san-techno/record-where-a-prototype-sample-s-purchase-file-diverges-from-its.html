Record where a prototype sample's purchase file diverges from its evaluation notes

Published by San Techno.

A practical guide for Singapore procurement teams on mapping where a prototype sample's purchase file and evaluation notes diverge, with routing rules, a divergence register and a handoff worksheet that keep confidential technical detail in authorised systems.

Why the purchase file and the evaluation notes drift apart

A prototype sample usually generates two parallel paper trails. The purchase file records what was ordered, who approved it, what was received and what was paid. The evaluation notes record what reviewers observed, what they compared and what they concluded. Both are legitimate records, and both are usually maintained by different people with different habits.

Divergence is normal, not a sign of failure. The purchase file may name a sample by an internal buying alias, while the evaluation notes use the wording printed on the supplier's sheet. A receipt may be logged on one date and first examined on another. A reviewer may add a note about a second sample that never appears in the purchase file at all.

The risk is not that the two records differ. The risk is that nobody can say where they differ, so a later reader treats one as a substitute for the other. This guide sets out a routing structure that records divergence without merging the two records and without copying confidential technical content into procurement systems.

That breadth is useful context here: a prototype sample file may relate to silicon wafers, to a power module concept, or to a botanical extract, and the same administrative discipline applies to each.

Start with a divergence register, not a merged file

The simplest control is a single register that sits beside both records rather than replacing either. Each row describes one point of difference, not the underlying technical content.

A workable row has six fields: a register reference, the purchase file reference, the evaluation note reference, a short neutral description of the difference, the role that owns the next action, and a status. The description should be administrative. "Sample named differently in the two records" is useful. A paragraph about what the sample is made of belongs in the authorised technical system, not in the register.

Keep the register short. If a row needs more than a sentence to describe the difference, the difference is probably a technical question that should be routed to the team that owns it rather than resolved in procurement.

A suggested review rhythm, offered as an author heuristic rather than a rule, is to scan the register at each receipt event and again before any file is closed. The point is to catch divergence while the people who remember the context are still reachable.

Separate the four kinds of divergence

Most differences fall into four groups, and each needs a different owner.

Identity divergence: the sample is called one thing in the purchase file and another in the evaluation notes. The fix is an alias field, not a rewrite of either record. Record both names and who confirmed they refer to the same item.

Timing divergence: the receipt date, the first examination date and the note date do not line up. Record all three dates as they appear. Do not adjust one to match another.

Scope divergence: the evaluation notes cover a question the purchase file never asked, or the purchase file covers a quantity the notes never mention. Record the gap and the role that can close it.

Status divergence: the purchase file shows the sample as received and closed, while the evaluation notes show the review as still open, or the reverse. This is the most consequential kind, because a closed purchase file can look like a settled matter.

For status divergence, add an explicit line stating that closure of the purchase file does not imply acceptance of the sample. That single sentence prevents a great deal of later confusion.

Route each record to the system that owns it

A routing rule is more durable than a shared folder. Write down, in one page, which system holds which record and who may change it.

Purchase records, approvals and receipts belong in the procurement system. Evaluation notes belong with the reviewing team. The divergence register is a pointer record: it holds references and short descriptions, never the substance of either file.

Confidential technical detail stays in authorised systems. San Techno notes that detailed architecture, materials, dimensions and assembly processes for its power module work remain confidential. That is a useful reminder that a procurement register is not the place for technical content, whoever the supplier is.

Two practical tests help. First, could this register row be read aloud in a meeting without disclosing anything sensitive? Second, if the register were lost, would any decision become impossible? If the answer to the second is yes, the register is holding too much.

A handoff worksheet for the divergence review

Use this worksheet as a template. The fields are administrative and the example values are fictional.

Register reference: DIV-014. Purchase file reference: recorded in the procurement system. Evaluation note reference: recorded by the reviewing team. Difference type: identity. Short description: sample appears under a buying alias in the purchase file and under supplier wording in the notes. Confirming role: purchasing lead. Status: open, awaiting confirmation that both names refer to the same item.

Second row. Register reference: DIV-015. Difference type: status. Short description: purchase file marked closed after receipt; evaluation notes still show an open question. Confirming role: reviewing team lead. Status: open, with an explicit note that purchase closure does not imply acceptance.

Third row. Register reference: DIV-016. Difference type: scope. Short description: notes reference a second sample not present in the purchase file. Confirming role: receiving team. Status: open, pending a check of whether a separate purchase record exists.

Keep the worksheet in the same place as the register and review both together. If a row stays open across two review cycles, escalate the ownership question rather than the technical question.

Keep the register honest over time

A register decays quietly. Rows get closed without a note, references drift as files are renamed, and the register slowly becomes a list of things that were once true.

Three habits slow that decay. First, close a row only with a dated note naming the role that confirmed it. Second, when a file is renamed or moved, update the reference in the register in the same action, not later. Third, keep one unresolved row visible even after the surrounding work is finished, so the record shows what was never settled.

Be careful with language. A register entry that says a difference was "resolved" invites a reader to assume the sample was accepted. Prefer "reference confirmed" or "ownership reassigned" where that is what actually happened.

None of that tells you how to record your own file. It does illustrate why procurement records and technical records are best kept distinct: the technical questions are substantial, and the administrative record should point to them rather than paraphrase them.

What good looks like at file closure

Before a prototype sample file is closed, run a short check. The purchase file and the evaluation notes should each be findable from the register. Every open divergence row should have a named owner and a status. No row should contain technical content that belongs elsewhere. The closure note should state plainly that closing the purchase file is an administrative act.

A useful final test is to hand the register to a colleague who was not involved and ask them to explain, in one minute, where the two records differ and who is dealing with each difference. If they can, the structure is working. If they cannot, the register is either too detailed or too vague.

For teams that want to see how San Techno describes its own materials and development work in public, the resources section is a sensible next stop. Read it as supplier context, not as a model for your internal records.

Divergence between a purchase file and evaluation notes is not a problem to be eliminated. It is a fact to be recorded, routed and owned. A short register, a clear routing rule and a disciplined closure check will do most of the work.
